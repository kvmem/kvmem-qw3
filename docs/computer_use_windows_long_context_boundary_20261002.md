# Windows 原生 Codex / QW3 长历史边界诊断

初始两条真实模型诊断均在约 317K 输入处报 KVMem 选择预算错误，未到自动压缩点。
现已隔离并修复缓存恢复路径的保留边界错误；六条原始请求开关重放通过。
随后明确延长诊断的传输等待并启用连接心跳，Windows 原生 Codex 已实际完成
945,446 token 的压缩请求、恢复后续观察并正确保留首尾标记，独立审计通过。
这是接近 1M 的合成压力输入组件验收，不代表复杂业务任务或任意 1M 历史可靠。
此前预算错误、传输超时和磁盘写满的失败全部保留，未归因于显卡容量不足。

这是单独的共用平台压力诊断，不计入已完成的十个自定义能力场景，更不计入原十个 OSWorld 衍生场景正式结果。真实推理使用固定 QW3 + DFlash2 和 Windows Codex 0.159.2；每次 `observe` 读取真实 Windows 截图，并附约 60K token、明确标注为合成的中性历史记录。只有只读观察工具，没有桌面动作。要求观察 17 次、保留第一与最后的标记；自动压缩阈值保持 950K。重复填充不代表普通桌面负载或日常延迟。

## 原因及反证

第一条失败时，初步怀疑历史截图强制保留会连带扩大文本。第二条反证显示，仅切换截图为可检索保留仍在同阶段发生同一错误，所以截图策略不是充分解释。

两条的请求计划均报告 509 个必须保留块、493 个新后续块，按 128 token 一块约为 65K / 63K，计划数低于 131,072 token 选择预算。实际最终选择却分别要求保留约 193K / 191K，再加 sink，超过该预算。两条都复用了 127,744 的 P 检查点，实际需重新处理的后续内容约 189K，而当前新观察只有约 63K。成功请求的首 token 等待也随这段后续内容增长。

**初始诊断已确认：计划与实际强制保留的范围不一致，预算检查触发了正常错误退出。**
旧 P 检查点之后重新处理的历史被当作完整 live suffix 保留的假设，现已通过
以下原字节输入控制和候选修复进一步验证。初始两条没有修改引擎，其原结果不改。

## 第一次修复后原生复测：传输与证据收尾失败

`long-context-on-03` 保持原配置、填充规模和 950K 自动压缩阈值。
完成 15 次只读观察，最大**完成**输入为 883,355 token；随后原生 Codex 发起
945,461 token 压缩请求。该请求 181.164 秒后报 `Timeout on reading data from socket`，
原生回合在 1,311.252 秒以失败结束，压缩完成次数为零、未交付首尾标记答案。
945K 是引擎日志中的**尝试**输入；没有已完成请求的实际用量，不能算成完成容量。
此次采样整卡峰值约 44.88 GiB、引擎 RSS 峰值约 50.24 GiB；未观察到 GPU OOM。

桥接层和宿主机转发层均使用 180 秒 socket 读超时。长输入压缩改变工具模板，
当前压缩请求重新进行预填充，日志在超时前仍有进展。已确认原生错误为传输读超时，
不是原先的强制保留预算错误；更长时间是否能完成及是否保持信息，仍须独立验证。

根盘写满又使采样器与录屏收尾报告失败，宿主机原终态报告未落盘。
恢复后保留不完整的 `native-incomplete-preserved`，从已存在的来宾机原件补收并
逐文件校验；新宿主机报告明确标记为恢复报告。第 16 条转发终态回执缺失，
独立审计保留这一失败。原始 MKV 和未完成的录屏清单不改；恢复可播放片段为
1,275 秒，短于整个原生回合，明确属于不完整录像，不计为连续录像验收通过。

已把关闭的早期归档迁到既有 `/data` 测试历史盘，22,834 个文件、约 11.68GB
逐文件核对哈希、权限和时间，原路径保留链接，未删除旧实验或其他工作。
原生桌面试次新增至少 8 GiB、长历史探针至少 2 GiB 的启动空间检查；采样器异常
会记录为基础设施错误并继续其余终态收集。新异常收尾分支仍需后续原生验收。

这些结果将可完成压力输入从初始约 253K 推进至本次约 883K；它们仍不是业务任务
成功或普遍上下文上限。该次失败时仍未验证长预填充的传输等待和压缩后保持能力；
后续第四次运行的验收结果见下文。

关闭状态也单独重放了开启版已完成的 883,355 token 原字节请求，928.669 秒完成，
返回合法观察调用，实际用量匹配。整卡峰值约 66.84 GiB，没有观察到 GPU OOM。
原生开启版在已有前缀状态下，同条请求桥接用时 92.082 秒；关闭版为冷处理，
视觉缓存状态和请求路径也不同。此项确认在本机可以完成该输入，不定义绝对容量
上限，也不是严格速度因果比较。900 秒左右的推理等待会超过现有 180 秒转发限制，
所以“在原生应用中失败”不能等同于引擎不支持该输入。

连接修复候选保留默认后端总等待 600 秒、读等待 180 秒，允许诊断明确指定更长
等待，并每 30 秒发送无用量、无工具输出的连接存活事件。总等待、读等待和取消
仍有效；真实 Codex 接收重复事件、超时、取消及不重复执行工具已接入合同检查。
打包仅携带此前已验证的原生运行检查，宿主机场景评分测试留在仓库中。
候选客户端 14 已在 Linux 和 Windows 各通过 77 项运行合同检查，包含真实 Codex
接收重复存活事件；推理后端为确定性脚本，不代表 QW3 长输入压缩已通过。
实际模型复测结果见下文；未替换已验证客户端 13，也未保存新正式快照，不计为 V1 收益。

## 延长等待后的原生实际模型验收

`long-context-on-04` 使用已通过 Windows 运行合同检查的客户端 14 和相同修复后
引擎。保留原 17 次观察、约 60K token 每次填充、pin-all、950K 自动压缩阈值、
1,800 秒任务预算、131,072 选择预算及 65,536 生成预算。诊断明确指定后端总等待
1,200 秒、socket 读等待 900 秒；桥接每 30 秒发送连接存活事件。生产默认等待
未修改。这是已披露的连接配置修复，不能称为单一代码变量或 agent 策略收益。

实际原生回合 **1,673.287 秒正常完成**，19 次推理全部成功并绑定原请求转发回执。
其中压缩请求实际输入 **945,446 token**，用时 **492.708 秒**，输出 455 token；
原生 `contextCompaction` 完成一次。恢复工具后的首个请求输入降至 **2,519 token**，
随后完成剩余两次只读观察，最终准确交付第 1、17 次标记及观察数。
心跳属于连接事件，不能把它计为模型首 token 或生成速度。

独立审计的 13 项检查全部通过，绑定实际用量、引擎 trace、原生事件、
全部请求回执与真实标记。连续录像完整 **1,692.5 秒**，包含启动和收尾。
采样整卡峰值 **44.90 GiB**、引擎进程树 RSS 峰值约 **50.79 GiB**；没有观察到 GPU OOM。
运行结束桌面仍暂停，仅停止本任务持有的引擎，释放显卡。

由此确认初始约 317K 失败并非绝对容量上限，180 秒读超时也不适合此次 493 秒
压缩请求。本机开启版可以通过该合成近 1M 组件验收；只验证两枚标记保持，
不验证完整业务语义、更多规则或任意截图历史。关闭版尚未完成同规格原生压缩
配对，不能从开启版成功和关闭版 883K 冷处理控制推断其压缩成功率或速度比。

## 验收与后续

宿主机独立审计绑定请求规范化哈希、VM 转发回执、引擎清单、原生事件、实际用量及连续录像。通过要求包括：压缩请求本身实际超过 900K、用量与引擎 trace 一致、压缩事件完成、恢复工具后上下文减小、第一和最后标记正确。前三次原生运行未通过，第四次全部通过；原失败结果不改。四项审计控制已验证：小用量不能因普通请求声称 950K 而通过、请求变化不能复用旧回执、引擎用量不一致不能通过、丢失标记不能通过。

开启版的实际压缩与两枚标记保持已验收。后续仍须完成 KVMem off 同规格原生
诊断、明确正式连接配置、验证退出行为并保存新共同快照；客户端 14 目前仅用于
这条显式诊断。它们属于冻结正式 V0 前的共同平台正确性问题，不作为 agent V1 收益。
原十场景正式运行仍为 0，006 的原简历仍缺失；十个自定义能力配对的结果单独保留。
