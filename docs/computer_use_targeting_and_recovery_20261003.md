# Windows 定位工具与恢复流程改进

2026-10-03。当前选择是：系统提供匹配的可见控件时，模型选择控件编号，程序负责取得
像素中心；没有匹配控件时，模型明确返回 `normalized_1000` 视觉坐标，程序根据当前截图
换算；每次操作后查看结果。界面中的控件名称只作任务数据，不能改变工具权限。

## 依据与判断范围

- 既有坐标对照：像素要求 0/12，显式归一化加程序换算 11/12，剩余一次为字符串类型
  错误。六个新目标来自已见截图，不能证明陌生界面、密集文字和自绘画布没有视觉问题。
- 既有推理对照：截图 thinking 关闭/开启分别 14/24、24/24，等价文字分别
  16/24、24/24。这是十二道短页面题各重复两次，复杂长任务仍需独立验证。
- 既有恢复失败：模型把动作编号放错层级，十四次错误调用未派发任何桌面输入。另一类
  问题是不同任务共用执行器历史编号。两者属于工具协议和恢复流程问题，不能当作
  点击准确率证据。

## 两项恢复修复与独立定位候选

client31 包含按任务隔离动作编号、精确字段错误反馈和有界恢复。连续三次已确认未
执行的拒绝暂停；连续至少三次观察且同一前台画面三十秒没有变化暂停；变化中的加载
进度会重置时间窗口，活动软件任务使用自己的回执和轮询。暂停阈值不保证一次长推理
也在六十秒内结束。Windows 原生 Codex 契约检查 138/138 通过。

client32 定位原型进一步提供 `act` 的 `click_control`；最终验证候选 client33 保留该接口：

```json
{
  "desktop_id": "从当前观察复制",
  "observation_id": "从当前观察复制",
  "action_id": "click-name-001",
  "action": {"kind": "click_control", "control_id": "ctl_0123456789abcdef"}
}
```

控件编号由程序生成并绑定桌面和观察，模型不能通过名称模糊匹配、猜测坐标或复用旧
编号。只给系统可见、启用、非密码控件且中心在截图/控件范围内的条目提供编号。
编号不存在、观察过期、无障碍接口超时或混用归一化单位均拒绝，指出具体字段。
控件点击仍通过既有 GUI 执行器进行一次左键输入，保留焦点与权限检查，不执行任意
脚本。动作前后屏幕仍必须核对；编号并不能证明模型选择的按钮符合用户意图。

原始选择、匹配控件、最终像素动作和回执均持久化。响应丢失后查询原回执，不根据新
界面再次定位或重复点击。视觉 click/scroll/drag 保留原显式坐标接口，用于自绘画布等
系统未暴露的区域；旧像素调用保持可用。

## 运行与验证

- 定位原型宿主打包契约：143 项，139 通过，4 项因 Windows/原生 Codex 条件跳过。
  新测试涵盖重名控件、旧编号、错误单位、坏坐标和丢失响应后的重开核对。
- 原 P3 基线有效试次共十六：十三次无人干预成功、一次正确保存但不确定暂停、两次
  业务失败。另保留一次基础设施中断，不能从总尝试记录中删除。
- 中断发生时，客机已停止桌面并留下推理流断开结果，宿主队列、模型、转发和录屏进程
  已不存在，原录像未正常终结。收集原状态后，以新身份同条件补测，不复用旧目录、
  不清空执行器历史编号。十五次原基线与一次补测分别通过证据审计。
- client31 同条件候选十六次使用冻结包，全部完成并审计。新定位接口不加入这组对照，避免把
  恢复修复与新增定位工具混在一起解释。
- 第四次 client31 实测（outside_scope）连续尝试最小化、点击和 ALT+TAB，三次均因
  前台窗口不在权限范围而拒绝，20.17 秒暂停但业务未完成。原权限允许 `open_app`
  激活指定任务应用；泛化的拒绝提示未说明这条路径。暂停减少了无效循环，却可能
  提前终止本能恢复的任务，不能仅因耗时降低就称为改善。
- client33 在提示和结构化错误中明确上述允许的恢复路径，不自动操作、不扩大权限，
  保留三次拒绝暂停。宿主完整打包契约 144 项，140 通过、4 跳过。新测试核对提示、
  无实际自动派发及原暂停计数。client32 等待队列在任何 VM 操作前停止，归档保留；
  client33 在 client31 冻结对照结束后，通过 Windows/原生 Codex 144/144 项契约检查
  以及另一组十六次真实本地模型同条件验证。
- client33 无人干预完成 14/16，实际产物正确 16/16，工具错误两次，执行器拒绝为零；
  两次保存回复丢失均在约二十秒后暂停，保存只执行一次，不计为无人干预完成。
  前台范围外条件两轮均通过允许的 `open_app` 路径恢复，未改权限。
- 55 次 `click_control` 的原始选择、对应观察中的唯一控件、像素映射和实际执行器
  事件逐一核对一致：53 次本地收到完成回执，两次本地不确定但远端确实完成一次。
  这证明本组绑定和派发正确，不证明所有界面上的语义选控件或视觉定位准确率。
- 任务耗时中位数：基线 87.39 秒、client31 46.40 秒、client33 50.30 秒；最终版本
  相比中间版本多了定位接口和焦点恢复提示，不能单独归因于定位工具，也不能因
  client31 失败时更快暂停而称其效率最好。最终版本与基线同时无人干预完成的十三对
  耗时中位数分别为 50.07 和 78.29 秒，仍只是本组描述统计。

## 当前适配方案与下一步

当前使用“系统控件编号优先 → 显式归一化视觉坐标兜底 → 操作后验证 → 有界恢复”。
安装和环境修复继续走受控软件工具，GUI 用于定位界面与验收交付；不要求模型把可由
程序确定的像素换算、动作身份和安装参数全部推理出来。这是根据目前证据选出的
适配方案，尚无依据称为所有应用上的最优方案。

下一步需要把控件编号与视觉兜底放到未见过的原生软件、不同缩放和自绘画布上作配对
验证，同时测试同名按钮、控件缺失/移动、焦点变化。分别统计语义选错、几何误差、
协议拒绝和任务成功，避免混为一个“视觉失败”。另外两次回执丢失仍由用户接管；
应单独验证只读回执核对能否安全解除不确定，不能用自动重发代替。

本轮 KVMem 与顾问均关闭。长历史的 KVMem 对照、原复杂场景、普通物理机/macOS 和
顾问集成尚未被这组短任务覆盖。
