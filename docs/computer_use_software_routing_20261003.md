# Python 修复流程的工具选择与作业身份优化

2026-10-03。保留此前正式 Python 新建 3/3、修复 3/3 通过的冻结记录；以下为新增开发
对照，不增加正式验收分母。真实本地 QW3 + Codex + Windows VM；thinking 开启、KVMem
关闭、DFlash2 开启、顾问关闭。每次重建同一缺包/错误启动器故障、重新启动应用和引擎；
复用已验证的依赖缓存和 VM 操作系统。

## 从正式试次发现的问题到修改

此前三次修复均出现 action_id 与旧任务重复；两次还尝试调用未实现的资源读取工具。
现在将模型 action_id 的幂等作用域限定在当前任务，内部作业 ID 由任务和 action_id
共同生成。相同任务的重试去重，不同任务可使用相同 action_id；跨任务查询仍被拒绝。
旧作业记录及旧版本相同任务重试保持兼容，不改写历史证据。

应用的模型入口只提供实际实现的 observe、act 和显式启用的 software 工具，并拒绝
返回未提供的工具调用。既有历史调用仍保留在上下文；通用协议桥默认行为未改变。
在真实复测中，完整 Codex 工具调用数与应用预算计数相同。

客户端 25 实测虽然零错误，但模型打开资源管理器浏览项目，地址栏自动补全又导航到
其他目录。模型自行放弃该绕路后调用软件作业，最终通过。这提示“零工具错误”不足以
衡量效率。客户端 26 仅修改软件模式说明：支持的安装/修复由软件作业提供诊断和验证；
只有目标或结果需要界面操作时才使用 GUI，避免重复检查文件夹。
