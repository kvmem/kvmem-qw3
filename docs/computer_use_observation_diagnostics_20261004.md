## 联系人字段

联系人05、06的姓名和电话均正确保存，原邮箱与其他联系人保持不变。05在600秒预算内未完成收尾，06在588.48秒、22调用内完成。

两次原始观察都保留了输入框value。发给模型的精简观察删除与name相同的value，因此模型看到的是`name: Local Pilot`，没有单列值。实际输入框没有提供可用的resource_id；control_id仅对一次观察有效，也不能直接当成跨观察的稳定身份。

当前`control_value`按唯一且完全相同的name选择控件，再检查value。模型用旧内容`Pilot`选择输入框，写入`Local Pilot`后，name随值改变，条件便无法匹配。电话输入`+12025550186`后，显示为`+1 202-555-0186`；这个格式差异也必须明确处理。05还长期保留未实际观察到的`First name`控件条件；06主动放弃这些无法证明的条件后完成保存和最终核验。

优先改进是明确区分控件标签、内容与身份：保留可编辑字段值；报告名称来自文字、描述还是资源标识；仅在设备真实提供稳定身份时支持条件绑定。缺少身份时明确返回限制和已观察候选，不能凭位置或旧文字猜出稳定身份。电话号码只允许明确声明、可审计的格式规则；不将所有字符串检查改成模糊匹配。

证据：`.runtime/candidate49-contacts-condition-diagnostic-01.json`，包含两次独立产物检查、模型声明的未满足条件和原始SQLite观察的哈希。记录中的value空缺须区分精简视图与原始证据。

## Android浏览器确认页

浏览器06（441.66秒、20调用）独立检查六个字段与只保存一次均通过。最终截图清楚显示`Request saved`、姓名、邮箱和详情；然而UiAutomator2观察仅有WebView及浏览器工具栏，没有正文子控件。`control_text`无法证明这些文字，应用保持暂停，原失败保留。

控件树在填写与预览阶段曾暴露正文，最后一页缺失不代表整次读屏失败。需要补充对可见截图的正向文字观察，并保留来源、区域、截图身份、识别器版本、模型哈希、耗时与置信度。仅凭模型结束发言或`screen_changed`不能替代最终核验。文字识别不能证明不可见内容、控件不存在或操作恰好执行一次；这些仍需回执和独立业务检查。

以固定[RapidOCR](https://github.com/RapidAI/RapidOCR)3.9.2、ONNX Runtime CPU及PP-OCRv4移动模型进行第一项离线诊断：在原1080×2400确认截图中，1.365秒识别22行，四项声明文字均能在仅折叠空白的正向文本检查中找到。不使用GPU、云端或设备输入，不修改任务验收。这只是单张英文截图：置信度不是校准后的正确概率，诊断的行拼接也尚未作为生产验证器启用。

证据：`.runtime/candidate49-android-browser-completion-diagnostic-01.json`和`.runtime/ocr-qualification/screenshot-diagnostic-01.json`。模型从官方版本地址下载，取消HTTP/HTTPS/ALL代理，下载后核验官方SHA256；依赖安装在项目独立目录。

进一步增加了可选观察器原型`visible_text_observer.py`：每份证据绑定截图哈希、观察/设备/会话/显示身份及区域，使用独立CPU子进程、显式本地权重和版本，禁止Python网络连接并关闭ONNX遥测；只支持正向文字证据，不自动变成控件、不发送输入、不替代业务评分。12项边界检查通过，包括旧截图、低置信度、越界、跨列拼接、无条件模糊匹配、过量输出及超时。

六张保留的三平台英文浏览器确认截图在宿主机全部完成识别（总调用1.49至2.52秒），20项原声明文字中17项可由严格短语规则证明，18个明确缺失的反例短语均未误报；只有3/6截图的全部文字条件都能证明。这是已知截图的条件覆盖，不能称为普遍OCR准确率。Android两张截图把`Keep`后误识别出句号，尽管置信度约0.991，严格检查仍失败；Windows一项失败来自原条件只包含行内子串，而原型要求完整文字行。原条件和置信规则没有为通过测试而放宽。

沙箱进程的首次验证还出现8秒超时、退出阻塞及负例截图选择错误，01/02/03失败记录全部保留。添加响应分帧、子进程退出等待上限和线程限制后，在实际应用的宿主机进程环境完成04；这不能据此认定所有沙箱退出问题已经解决。原型仍未接入当前模型任务，需继续验证生命周期与真实模型调用。

追加证据：`.runtime/ocr-qualification/multiplatform-qualification-01.json`至`04.json`。后续应先判断文字误读、谓词覆盖和执行开销是否可接受；不能因为加入专用OCR就假定一定比QW3视觉理解更好。
