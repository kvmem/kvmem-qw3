# DFlash 2 单请求：状态重验与内核筛选（第三阶段）

继续使用 Qwen3.8-27B Q8_0 主模型、E4M3 FP8 KV、官方 BF16 草稿和原有内部
算术。未增加 BF16 主模型/KV 支持，未部署，多并发仍后置。本记录不修改前两
阶段已经封存的报告及原始数据。

## 当前候选的归档恢复

在与第二阶段公开格式对照相同的 CLI binary 上重新运行完整的归档测试：
`b75009375182e734f14ea90ae6c6270c48ef4bef90dfd20a76e461fe57419d7f`。
显式开启 SwiGLU reuse=1、GPU target sampling、七草稿，FP8 KV、CB 关闭；
归档窗口 1024、生成窗口 512。每个测试进程的环境、命令和 SHA 均已记录。

`benchmark/dflash2/q8_archive_c1_selected01/validation.json` 中 **12 个独立
进程、54 项断言全部通过**。包括有/无 DFlash 的 4K 归档目标 KV/token/ladder
逐字节一致，4K 直接恢复、3K 残余重放、旧归档冷启动草稿，以及从 4K 检查点
续建到 8K。续建和连续构建的 raw K、V、tokens、新 ladder（包括草稿缓存）
逐字节一致。这是持久化检查点恢复模拟，不是断电/文件系统崩溃一致性试验。

原有测试在最后两次 8K 查询中只检查了各路重复输出，未直接比较跨算法结果。
新增 `benchmark/dflash2/audit_q8_archive_responses.py` 补齐这一点，并检查全部
四组查询的非计时字段：文本、token 数、检索索引、私有查询/重放状态等。
**8 组跨算法响应/状态比较全部通过**，覆盖 16 条响应，证据为该目录下的
`response_semantics_audit.json`。这是补充验证，不把旧的有限检查扩大解释。

## 32K bounded KVMem

恢复原内核源码后，重新构建生命周期 probe 并完成 32K 历史检查，16 个步骤
全部通过：两路历史摄入、首次/热查询、历史增长、尾部改写、取消、取消后续写、
旧前缀分叉。DFlash 与同策略无投机响应完全一致。证据为
`benchmark/dflash2/q8_lifecycle_validation_c1_selected01.json` 及对应日志。

该 probe 使用固定 256 个 slot、每块 32 token，保留上限 8192 token，窗口
1024、生成窗口 512。它验证 32K 逻辑历史下的有界保留策略，不是将所有历史
KV 常驻 GPU。回退到较早前缀时约需 25 秒完整重放；这项开销没有计入短查询
吞吐，也不能据热查询性能承诺任意前缀回退同样快速。这些时间仅为正确性运行
的诊断，不是正式性能测量。

随后同一 probe 的 **128K 历史 16 个步骤也全部通过**，两路输出一致，固定
slot/保留窗口策略不变。证据为 `q8_lifecycle_validation_c1_selected02.json`；
耗时约 840 秒，较早前缀重放约 98 秒。32K/128K 合计 32 个步骤，覆盖受限
保留、查询复用、改写、取消和分叉，不替代查询引导、压缩或真实任务质量验证。

## 寄存器占用试验已撤回

只为宽度 8、reuse=1、非 vector-load 的 SwiGLU 新增候选实例，调整 CUDA
launch bounds 的最低 CTA 数，不改数值运算。仅构建算子测试程序，CLI binary
保持不变。实际日志中的 90 个 linear 算例全部通过精确输出及边界保护检查。

候选从每线程 108 个寄存器降到 96，编译资源报告 stack/local 均为零。但
使用两个真实形状 gate/up 权重组轮换，工作集 378,798,080 字节，大于 L2 的
两倍（L2=134,217,728），五次交替测量的中位耗时从 **0.146061 ms 增至
0.182268 ms**，约慢 24.8%。未继续做模型吞吐测量，也未选入候选配置。

试验源代码、原始源代码、runner 和结果保留在
`benchmark/dflash2/q8_c1_occupancy_experiment01/`；算子和微基准日志分别为
`q8_c1_occupancy_operator01`、`q8_c1_occupancy_stream01`，编译资源为
`q8_c1_build10_resources01.txt`。运行源码和测试源码已恢复原 SHA，并重新构建
测试程序。不能将降低寄存器数本身视作提速证据。

## INT8 Tensor Core 独立原型未选用

新增独立算子构建入口 `benchmark/dflash2/build_q8_operator_variant.py`，只编译
实验文件并在链接时提供其 Q8 算子，不替换原 CLI、core archive 或运行源码。
原型文件位于 `q8_c1_mma_experiment01/`，用整数 MMA 计算八元素点积，保留
现有 Q8_1 scale、128 个浮点部分和及归约顺序。设计及 PTX 文档来源见其 README。

原型的 **90 项 finite FP32 精确/边界保护检查通过，memcheck 零错误**。
这里的精确检查是有限数值的最大绝对差为零，不扩大成正负零位模式也一致。
编译报告 175 寄存器/线程、stack/local 为零，反汇编包含 INT8 MMA 指令。

相同的轮换权重微基准中，五次交替测量的中位耗时为 reference **0.141866 ms**、
候选 **0.253125 ms**，慢约 **78.4%**。因此不选用，也不进入模型级吞吐试验。
`status.json`、`linear01.json`、`memcheck01.json`、`stream01.json` 及原始日志
记录结果。它证明该算子原型在所测形状上可保持现有数值，却不证明 Tensor Core
路线一定更快，也不证明未经测试的其它实现无法提速。

## 计时入口补充

公开输入 runner 现在额外记录每任务连续墙钟窗口：从第一个测量请求准备前，
到最后一个响应解析结束，排除 warmup/模型加载，计入请求间客户端记账开销。
摘要保留原来的 HTTP 请求耗时之和，同时单列 `task_wall_tok_s` 和
`client_gap_seconds`；旧记录不补造不存在的墙钟数据。这使后续完整任务测量
能明确对齐公开基准的整组请求计时口径。当前仍不是正式 128 样本/重复验收。

新增计时入口已用 GSM8K 两条测量响应和一条 warmup 实际验证，输出与第二阶段
对应响应完全一致。请求耗时之和为 2.527496 s，整组墙钟为 2.528373 s，
客户端间隙约 0.877 ms；两种吞吐分别 144.807 和 144.757 tok/s。这只验证
计时字段及输出回归，不能与此前八条样本的任务均值比较。证据为
`q8_c1_public_task_window_{summary,identity}01.json`。
