# KVMem 正式矩阵与输入冻结

目标仍在执行。主配置是 Qwen3.8-27B Q8_0 权重、E4M3 FP8 KV 和官方 DFlash 2
草稿；普通 QW3 只承担正确性与回归。当前冻结的是输入与验收规则，**尚未执行
这些长历史场景的正式推理、质量评分或性能测量**。

权威清单为 `benchmark/dflash2/kvmem_matrix_v2.json`，输入为
`benchmark/dflash2/kvmem_workload_v2/manifest.json`。所有原始 v1 文件和失败日志
保留。具体源码、二进制、优化开关和运行库还须在候选版本进入正式测试前冻结。

## 必需性能场景

历史长度是最终查询前的原生 token 数，另行记录查询与模板的长度。
每个场景测量 `max(16, 2×并发)` 个固定请求，按并发分波；预热使用独立的固定
样本。每条路线至少三次独立进程运行，轮换顺序；结果不明确时按计划增至
6、9、12 次，仍不明确则保留为未完成。

| 场景 ID | 历史 | 工作集 | 并发 | 状态 | 存储 |
| --- | ---: | ---: | ---: | --- | --- |
| `full_4k_c1_cold` | 4K | 8K | 1 | 冷 | 全部保留 |
| `full_4k_c4_warm` | 4K | 8K | 4 | 热 | 全部保留 |
| `sparse_4k_w256_c16_cold` | 4K | 256 | 16 | 冷 | 全部保留 |
| `sparse_32k_w4k_c4_cold` | 32K | 4K | 4 | 冷 | 全部保留 |
| `sparse_32k_w8k_c16_warm` | 32K | 8K | 16 | 热 | 全部保留 |
| `sparse_32k_w256_c1_warm` | 32K | 256 | 1 | 热 | 全部保留 |
| `bounded_128k_w8k_c1_cold` | 128K | 8K | 1 | 冷 | 16K 有界库 |
| `bounded_128k_w4k_c4_warm` | 128K | 4K | 4 | 热 | 16K 有界库 |
| `bounded_128k_w256_c16_warm` | 128K | 256 | 16 | 热 | 16K 有界库 |

全量可容纳场景使用 8K 工作集，确保 4K 历史加查询和模板确实能放下。
有界场景的库容量是 512 个 32-token 块，启用 delete GC；它会丢弃旧内容，
不是无限保留历史。会按事实位置报告绝对问答准确率，并只比较相同保留策略。

各路线统一 CPU plain mean-K 索引、query-conditioned 检索、强制重选、32-token
块、1 个 sink 块、2 个 recent 块、256-token prefill chunk、1024-token 生成
预留。性能请求 T=1、top-p=.95、top-k=20、top-k-first，最多输出 256 token。
每次移动 FP8 K 都从不可变原始 K 重建。其余参数、种子和样本序号在 JSON 中固定。

冷场景把历史构建计入请求窗口。热场景预先构建每个请求的历史，测量恢复、
克隆、查询选择、回放、生成和清理；同时单列历史构建及包含构建的总成本。
每一波使用共同起止时刻计算吞吐，各波按 token 总数除以窗口总时长汇总，
不累加请求 tok/s。decode 速度另按各请求首次到末次 token-ready 时间报告分布。

none、MTP 和 DFlash 均保留默认串行与完整连续控制器两种候选。默认串行维持
原有内部运算；每个候选分别通过质量门槛后再测量。每场景使用合格 none/MTP
候选中几何平均吞吐最高者作对照，保留全部重复测量和所有候选结果。

性能要求是九个必需场景等权吞吐比的几何平均点估计 ≥1.05，单侧 95% 下界 ≥1。
每场景不得出现超出测量不确定性的退化；若点估计略低于 1，95% 区间须包含 1
且半宽不超过约 2%。TTFT p95 和请求延迟 p95 的单侧 95% 比值上界须 ≤1.05。
统计方法、重采样和追加重复规则均已固定；OOM、拒绝、排队和未支持场景不能删去。

## 输入和质量

- 144 条合成输入：三种精确历史长度各 32 个正式样本、16 个预热样本，涵盖
  英文/中文检索、版本更新和多个事实。保存完整文本、token ID、查询边界、
  事实位置和目标标记；这些是检索与状态用例，不冒充真实任务得分。
- 132 条 LongMemEval-S 输入：六种类型各按 question ID 排序取前 17 个有答案
  样本，再加入全部 30 个无答案样本。原始记录、渲染代码、问题、答案和所用
  tokenizer 文件均记录哈希。保留完整历史，不截断以适应容量。
- 真实问答分别在 8K 工作集/完整保留与 4K 工作集/16K 有界库运行，并发 4。
  包含 greedy 和四个预先声明的随机种子，最多 512 输出 token；推理答案不会
  写回后续固定历史。

Greedy 要求相同策略下与默认串行 none 的输出 token 完全一致。真实问答另用
本地 Q8/FP8 无投机模型作盲评，采用固定的 LongMemEval 分类型评分提示词。
14 个独立正/负校准样本已冻结，尚未执行；校准失败或非法评分会阻止质量通过。
这是本地评分，不是官方榜单结果。

随机质量使用按问题聚类、分类型配对 bootstrap，保留每个问题的全部随机种子。
七个类别等权宏平均的单侧 95% 差值下界须 ≥−2 个百分点，各类别须 ≥−5 个百分点。
同时报告绝对准确率和所有成对退化；区间过宽时按固定规则增加所有路线的种子，
不删样本或只重跑表现较好的结果。

## 分词问题与版本修正

第一版长问答的原生分词检查暴露了两个不同问题：

1. 原生实现用字符区段及 locale 近似 Unicode 类别，把部分全角标点当成字母，
   例如 `，《` 的切分不同。现在按模型 regex 引擎的实际字符集合生成分类表，
   并覆盖非 ASCII 数字、组合字符、Unicode 空白和补充平面字符。
2. Transformers 5.10.2 的 `Qwen2Tokenizer` 构造函数会重建 regex，省略模型
   `tokenizer.json` 中的组合字符规则。模型文件还指定 NFC 归一化，原生代码
   此前缺少这一处理。原生现补上 NFC；第二版输入直接使用模型文件的完整 pipeline。

NFC 实现固定为 [utf8proc 2.10.0](https://github.com/JuliaStrings/utf8proc/releases/tag/v2.10.0)，
源码、许可证和提交 `a1b99daa2a3393884220264c927a48ba1251a9c6` 随工作区保存。
分类表由固定 tokenizers 0.22.2 对全部 Unicode scalar value 查询生成；构建时
不需要 Python，运行时不依赖进程 locale。

第二版保留所有 276 条提示文本、样本 ID、事实位置、质量阈值和性能场景。
仅 10 个真实问答样本的 token ID 因 tokenizer provider 修正而改变，逐条记录于
`encoding_amendments.json`。此修正发生在任何模型推理前，旧输入及三次失败
分词审计仍保留。公开的 800 条输入及 107,581 个 token ID 没有变化。

## 本阶段已完成验证

`kvmem_frozen_inputs_validation01.json` 核对全部 276 条输入、22,470,544 个原生
token ID、查询边界、合成事实位置、输入哈希与矩阵配置。276 条原始提示文本
均未改变。Unicode 分类表重新生成检查通过，C locale 下分词回归通过。

NFC 会改变组合字符的字节长度，因此 HTTP 层的检索分组、harness 固定区域与
工具调用的活动后缀也补上原始字节到归一化字节的映射。落在被合成字符内部的
边界向外取整，空区域保持为空；测试覆盖重音、韩文组合、组合字符重排与长文本。
全部 36 项主机测试通过，CUDA CLI 与相关模型检查程序构建通过。

当前二进制的普通 QW3 回归通过 44 个响应。KVMem HTTP 验证分别在 none 与
DFlash 下运行 9 个响应，涵盖自动消息分组、显式分组、harness 固定区域、工具
结果活动后缀和组合字符内部边界。每路线四对 NFC/NFD 输入的输出与 token 数
一致，跨路线九对输出也一致；DFlash 原生日志确认实际执行 52 个投机批次。
这组输入为 549/829 token、工作集 1024 token，只验证接口与边界映射，不是
稀疏检索质量或长历史性能结果。前面三次因检索配置及生成预留不匹配导致的
服务启动失败保留在 `kvmem_unicode_http_matrix01/02/03.json`；第四次完整通过。

HTTP 的既有路线标签仍把 DFlash 标成 `plain`，本次以原生
`dflash_spec_summary` 确认实际执行。正式 HTTP 性能归因前还须修正该标签。
上一阶段 544 个控制器响应保留原源码身份，不标成当前分词改动后的全量验证。
`public_execution_protocol_v8.json` 登记本矩阵与审计哈希，沿用原目标阈值和
全部公开输入。冻结矩阵中的正式模型推理、裁判校准、质量和性能测量仍未执行。
