# 最早请求优先的长历史四并发筛选

2026-09-27，`concurrency_oldest01` 已完成。该候选让最早进入的请求优先完成
prefill，并在 prefill 块之间允许4轮已就绪验证。Q8_0、FP8 KV、每请求
K131072/G65536，长历史输入、种子1000、自然EOS/4096上限均与已有对照一致。
固定FP8 ragged attention开启；会话复用、私有query让出、宽Q8/SwiGLU均关闭。

32条刷新场景响应通过调度关闭/开启一致性。随后4条真实长历史输出共2076 token，
每请求token ID与 `integrated_concurrency02/reference` 完全一致；接受率均为31.725%。

调度显著减少输出停顿，但没有观察到整体吞吐收益。单次约0.53%的时间差不能当作
稳定回退结论。此处含prefill的服务吞吐不能与此前单请求纯decode吞吐直接比较。

候选646次验证全部只有1个就绪请求（643批8行、1批7行、2批6行）；已存对照有
28次四请求验证。四个请求被同时接纳不等于每次都能四请求合批，最早完成prefill
的请求可在后续请求仍处理历史时结束，因而失去批量摊销机会。这解释了更连续的输出
没有转化为整组吞吐提升。

保留该候选作为延迟策略，不继续围绕它重跑完整效率矩阵。下一步优先修复长历史
会话复用的冷/热分叉，并提高联合验证计算效率。最终仍需集成后的独立复验。

证据：`benchmark/dflash2/concurrency_oldest01/manifest.json`、
`candidate_analysis.json`、`prefill_refresh_c4/` 和 `oldest_candidate/`；
