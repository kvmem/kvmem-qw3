# 256K、10% 重算结果复核及 llama 实现对照

复核未发现能推翻原始 **54/60、90%** 成绩的评分或输入错误。六个样例、12 次全新进程对照全部完成，开关两组的检索分数与入选窗口相同，大幅提升在选取的四个多答案样例上复现。用户提供的另一实现存在数据、权重量化、位置和状态语义等差异，因此两边的增幅不能直接对比。

本次复核范围是此前开启组的全部 60 例原始记录，以及用户提供的 `/home/chaidi/kvmem-freetoken/kvmem-llama-cacheblend` 实现。没有修改两边的生产代码，也没有把诊断样例并入原来的正式成绩。

**原始 60 例的独立核验**

不导入原评分函数，直接从 HTTP 响应取 `</think>` 后的最终回答，以完整七位数字匹配重新计分。全部 60 例与保存的成绩一致：开启组仍为 54/60，答案覆盖率 90%；六个失败仍全部来自多键干扰。多查询 15 例还逐项核对了同一行中的名称—数字对应，全部正确。历史关闭组的原始回答也重新核对，仍是覆盖率 60.42%、整题全对 22/60。

同时核验了以下内容：

- 60 个 token 文件及文本文件 SHA256 与冻结清单一致，解码文本、Query span、证据位置均一致。移除标注的证据段后，输入剩余位置没有任何目标数字，包括问题、系统提示和样例标签。
- 每例均先执行短 reset；首个 65536-token ingest 的日志明确为 `base=0`、前缀缓存 MISS，之后只复用同例的 ingest 前缀。生成私有检索 query 不属于评分回答。
- 每例只出现一次 blend，均为 102 个完整块、3264 tokens、`missing_source_tokens=0`，随后执行 Query Replay。全部正常停止，没有 thinking compaction。
- 当前 Q8 权重文件 SHA256 与历史模型记录一致：`a680f44a06920e5d689774823782006aa3acc8db95750323373b24139b67e348`。复测使用原冻结二进制 `48b6415c4adfad971dd4a55896d59ea029a1861a7d8055df8aa834c2214f29cd`。
- 原结果未保存完整 HTTP 请求体，原始输入的请求构造由冻结 runner、配置与日志核验。本次冷启动对照另保存了实际发送的完整请求体，避免把原始记录的可审计范围说得过满。

**冷启动复测**

六例在运行前固定：两例多值、两例多查询，覆盖三个种子；另加一个单针成功样例和一个多键失败样例作为控制。每个样例的每个开关组都使用全新进程，共 12 次；组内请求、模型、Query 策略、MTP、输入与输出上限一致，仅修改 blend 比例，并使用不同的只读检索 dump 路径。开关顺序交替。

| 样例 | 关闭：答案覆盖率 | 开启：答案覆盖率 | 整题全对变化 |
| --- | ---: | ---: | --- |
| 同名四数字，10%，seed=1000 | 25% | 100% | 错 → 对 |
| 四名称查询，10%，seed=1000 | 75% | 100% | 错 → 对 |
| 同名四数字，70%，seed=2000 | 25% | 100% | 错 → 对 |
| 四名称查询，70%，seed=3000 | 75% | 100% | 错 → 对 |
| 单针，50%，seed=2000 | 100% | 100% | 对 → 对 |
| 多键干扰，10%，seed=2000 | 0% | 0% | 错 → 错 |

六例的关闭、开启成绩均与相应历史记录相同。两组实际发送的 reset、四次 ingest、answer 请求体逐项完全相同；命令相同；环境仅 blend ratio 和只读 dump 输出路径不同。六对均为相同的 1024 个入选块，dump 中每块检索分数的最大绝对差为 0，排除了此次 A/B 因召回窗口不同而产生收益的解释。dump 输出的入选块 token 也与原始输入相应位置逐项一致。

四个多答案样例共 16 个目标数字，按既有策略从 dump 重建的重算名单覆盖了全部 16 个完整数字。也覆盖了其中 15 个完整名称；另一个跨块名称只留下后半部分。部分事实缺少句首，因此“完整事实字符串”检查只命中 9/16，不能误写成全部原句都完整召回。无论关闭还是开启，窗口内容相同，但更新重要块的表示后，最终四个样例都能找全答案。

这使“10% token 为何有大收益”有了更具体的解释：所选 token 高度集中在关键数字附近，而不是均匀随机的 10%。它仍不能证明 GDN 临时状态、位置压缩、重算顺序各自贡献了多少。

本子集整题全对为 1/6 → 5/6、答案覆盖率为 50% → 83.33%；由于有意选择四个先前改善的样例，不能用该子集比例估计总体准确率。没有重跑完整 120 次开关实验。所有请求均正常停止，任务启动的 12 个服务进程均已退出。

**与用户提供的另一实现相比**

已完成的 llama 180 例测试位于 `/home/chaidi/kvmem-freetoken/benchmarks/cacheblend-ruler-3090-20260926`。本次读取其 256K 的 60 个实际 token 文件，统一转成 little-endian int32 后逐一比较，避免把 `.npy` 与原始二进制文件的不同封装误当作内容差异。按 `(task, length, depth, seed)` 配对，**60/60 token 数组不同、60/60 问题不同、60/60 答案集合不同**。

例如，多值、256K、10%、seed=1000：qw3 查询 `volatile-hanger`，四个数字为 `6321458 / 4344178 / 8920812 / 3373427`；llama 查询 `thinkable-literate`，四个数字为 `2663286 / 7603660 / 6921862 / 2055956`。相同 seed 标签不意味着生成了相同的随机内容。

| 项目 | qw3 的 256K 正式运行 | llama 已完成的 256K 正式运行 |
| --- | --- | --- |
| 模型权重量化 | Q8_0 | GSQ-RCO-IQ3_S |
| 主 KV | FP8 | Q8_0 |
| 召回窗口预算 | 32768 tokens | 36864 tokens |
| 重算量 | 3264 tokens，102 块 | 3680 tokens，115 块 |
| Query 表示 | 包含 guided query 生成 | 原始 user Query |
| RoPE 位置 | 压紧到召回窗口，`NO_REROPE=0` | 保留原历史位置 |
| 重算执行 | 连续段分别执行，61–80 次 forward | 可把不连续位置合批，60 例日志均为 4 次 forward |
| 重算前后 GDN | 清零一次，跨段推进，最后恢复 Query 边界 | 历史正式组日志为 carry，保留推进后的状态 |
| MTP | 4 | 3 |
| thinking／输出上限 | 4096／8192 | 12288／16384 |

两边都按检索分数选择完整块、再按历史／窗口顺序执行，比例相同不代表处理的证据、位置或状态相同。特别是 qw3 在压紧位置后重算，而 llama 保留原位置，重算要改善的表示偏差本来就不同。这是值得隔离的机制差异，不是已经完成的单变量因果证明；也没有实验能把全部差距归因于模型量化。

当前 llama 代码**已经支持** `--kvmem-blend-state reset-restore`，并有后续 GDN 对照。不能继续把“另一实现只能 carry”作为解释。本表专指归档的 180 例运行，其 60 个 256K 日志均明确记录 `recurrent=carry`。新建的 `cacheblend-gdn-hard256-20260927` 继续沿用 llama 自己的数据与 IQ3 配置；另有 `cacheblend-qw3-128k-20260927` 在对齐 qw3 的 128K 输入。它们不能替代双方同输入、同权重的 256K 对照；本次也未介入这些正在推进的任务。

**结论适用范围**

每类 15 例来自三组名称和数字在五个深度上的放置，并非 15 组完全独立内容。多值、多查询是在文章背景中查找四条事实；多键干扰的背景本身由大量同格式名称—数字事实构成，难点不同。高检索分数的少量块可能覆盖大部分目标事实，10% 的 token 比例不代表只处理了 10% 的有用证据。

完整 60 例的历史关闭组与开启组在二进制、guided MTP 开关和输出／thinking 上限上有差异，不能将 22/60 → 54/60 当作完整的严格单变量 A/B。之前已有 29 例同构建、同配置关闭组，本次增加更严格的全新进程复现。所有比较应同时保留答案覆盖率、整题全对和具体证据覆盖，不能仅用一个百分比解释实现优劣。

当前实现是按 Query 分数挑选完整块、经过全部模型层重算，并对 GDN 采用临时稀疏状态链的近似。它不等价于任何同样标注“10%”的 token 选择、分层重算或全窗口 recurrent replay。原始结果可以支持这一冻结设置中的收益，不能外推为其他实现必然有相同提升。
