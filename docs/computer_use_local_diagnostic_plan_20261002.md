## 1. 已知基线与尚不能下的结论

- 最新 12 行表格开/关均超时且缺失保存成果；权限拒绝和恢复失败干扰了能力判断。
- 模型请求固定 `enable_thinking=False`，桥接器拒绝 `reasoning_content`；尚未检验
  同模型开启 thinking 的实际效果，不能声称已经达到模型的推理上限。
- `open_app` 的完成回执不保证所需应用已获得前台焦点。
- 已有无进展检测主要针对完成的相同操作；重复拒绝、纯观测等待仍有覆盖缺口。
- 应用的“完成”主要表示模型回合结束并取得证据，独立业务判分仍在测试侧。
- 原十场景正式运行 0 次、V0 尚未冻结。006 原始简历缺失，051 从头完成的正向
  过程验证未完成，043 原规则和评分口径冲突仍保留。
- 缓存及 79 个历史归档已处理，系统盘最近实测约 70 GiB 可用；新运行前需重查。

## 2. 实验不变量

1. 主模型保持 Qwen3.8-27B Q8_0，匹配视觉编码器、DFlash2、Codex harness 和
   Windows VM。普通硬件容量和 Mac 不在本轮诊断验收内，也不宣称已经支持。
2. 先固定 KVMem 为 off、短上下文，减少检索历史对视觉/推理归因的干扰。
   完整任务摸底选定一个固定配置；最后才做独立的 KVMem 开/关比较。
3. thinking、图像呈现、恢复策略分别比较，不能在一组对照中同时换模型、量化、
   提示和执行器。DFlash2 全组保持相同；只有出现推测解码异常证据才增加 target-only 诊断。
4. 配对固定任务、输入文件、截图、客户端和引擎身份、快照、工具范围、采样参数、
   调用次数及时间预算。thinking 两侧保持相同总输出 token 上限；预算耗尽单列。
5. thinking 组必须确认后端实际采用推理模式。模型“说自己思考了”不算证据。
   不要求两组走相同轨迹，也不把不同轨迹的耗时直接解释为纯推理速度。
6. 参考答案、控件框和验收规则在测试前冻结。开发样本可用于修改；保留样本封存，
   只在候选冻结后评分。封存样本用过后不能继续被描述为未见测试。
7. 控件定位输入不附带答案坐标；放大采用预定分块或模型明确请求的区域，不能按照
   正确答案选取裁剪区域。坐标必须映射回原始屏幕，重复标签按目标身份核验。
8. 只更改一个已观察到的原因，每轮最多两个通用改进。失败、超时、无效环境和
   有效但未通过的任务保留，不用额外运行替换原失败分母。
9. 诊断完成条件是结果完整、可评分和可归因，不是模型全部答对。局部执行器问题
   只阻塞依赖它的实操测试，不能无限延后其余读屏和文字推理诊断。

## 3. 顺序、样本和交付

### P0：固定基线，排除接口和执行器假象

先保留当前 D0 配置及故障证据，再验证四类中性固定操作，各三次，共 12 次：
应用启动/切换、已知控件点击、精确文字输入、另存为并保留原件。这些是预定动作，
不经过模型决策，不计入模型成功率。核查前台进程/文档身份、输入内容和输出文件。

并行准备可选 thinking 支持，但不改变默认基线：核验推理段与最终回复的解析、
工具调用只在完整终止后交付、取消/截断行为、工具 ID 及历史连续性。检查历史
推理的保留语义；不能丢失必要状态，也不能将推理内容误当作可执行动作。
先做针对改动的接口检查，再用本地真实 QW3 做短回合和跨工具回合验证。
不重新运行与本次改动无关的全部历史测试。

输出：带源码/模型/引擎哈希的 D0、thinking 候选配置、12 次操作结果和剩余平台缺陷。
若 thinking 兼容仍受阻，先执行 P1；P2 的 thinking-on 单元保持未执行，不能用
“请逐步思考”提示替代真实模式开关。

### P1：读屏与定位，先测 24 个中性样本

四类各六题：小字/表格读取、按钮/字段定位、窗口/文档/弹窗状态识别、空间与选中
区域判断。覆盖 Edge、Notepad、Calc、Writer、Impress 和 GIMP 的中性素材。
每类三题开发、三题保留，共 12/12；不使用原复杂任务保留组轨迹调提示。

比较固定原图与预定分块放大，两组均为 thinking-off、KVMem-off，共 48 次读屏请求。
一次请求可以带固定的多个图块，图块数量、像素和图像 token 单独记录。

指标：OCR 字符/字段准确率、目标框命中率、坐标误差、状态识别准确率、回答格式
错误、每次响应耗时和视觉输入量。人工核对答案只供评估器使用，不交给截图组。

输出：具体到应用及控件类型的错误矩阵。放大改善提示细节/分辨率瓶颈；稳定误认
图标或控件身份提示感知/定位弱点，仍不能单凭一次对照断言根因。

### P2：思考推理，做同信息的 2×2 对照

12 个独立规则题，包含约束计算、最新规则覆盖旧规则、跨材料选择、操作顺序与
验收判断，各三题；每类两题开发、一题保留，共 8/4。题目不能依赖隐藏材料。

同一题提供两种输入：原始截图；人工核对过的等价结构化事实。文字保留全部可见
事实、顺序和干扰项，不提供解法、下一步动作或额外隐藏信息。

四组为“截图/文字 × thinking-off/on”，每题每组两次，合计 96 次请求。
优先采用同一采样参数和预先分配的运行顺序，重复运行用于揭示波动而非挑最佳答案。

指标：全部约束满足率、规则版本选择正确率、结论/计划正确率、自检纠错率、预算
耗尽率、总时延及输入/输出 token。模型解释是否流畅不作为通过依据。

归因规则：
- 截图错而等价文字对：感知或视觉事实提取可能是瓶颈。
- 文字组也错：推理、规则理解或任务表达仍有问题，需要审查题目后归因。
- 同输入 thinking-on 改善：推理预算可能有效；同时报告它带来的时间和资源成本。
- 四组都对但实操失败：回到执行和恢复层，不能继续归咎于读屏。

本组是诊断辅助输入，不计入真实 computer-use 成功率。差异只提供原因线索，
归因仍需回看首次错误和动作回执，不给“视觉占多少、推理占多少”的伪精确比例。

### P3：故障恢复，用六种固定异常比较原/优化流程

六类故障：焦点在其他窗口、普通保存确认弹窗、前台超出操作范围、界面延迟更新、
误入其他页面、操作投递结果不确定。使用中性窗口和测试文件；不需要真实付款、
真实账户或放开应用权限来制造条件。

在 P2 选定并冻结本地推理配置后，原流程/候选流程各重复两次，共 24 次故障试验。
另加正常响应、正常慢加载两个无故障对照，各流程各两次，共 8 次；本阶段合计 32 次。
每次最多 180 秒、40 次工具调用。合法等待范围和进度检查点在运行前固定。
恢复检测必须覆盖反复拒绝、只观测不行动、错误窗口，以及正常但较慢的加载。

优先候选：可靠确认目标应用/文档焦点；对持续无进展采取有界恢复或明确交还用户。
不确定投递沿用核对后恢复规则，不盲目重放。自动恢复、正确请求接管、卡死、
错误恢复分别计数；请求接管不算无人干预完成。

指标：自动恢复率、可控结束率、停滞发现时间、无效动作/观测次数、额外恢复耗时、
错误窗口输入和重复写入。候选操作目标为停滞后 60 秒内恢复或明确请求接管；
这是待验证目标，不是已达到能力。误触发恢复率也必须报告。

### P4：完整任务能力阶梯，确认真正的可用范围

选择三个可独立验收的任务族：表格公式/排序、办公文档指定修改、多材料规则与
文件归档。每族三个难度，每级三次，共 27 次。分别只提高行数、修改点数量、
材料数量，其他要求和干扰条件保持一致；建议规模为表格 3/12/30 行、文档
2/5/10 个修改点、材料 2/5/10 份，具体实例在第一次运行前冻结。

每个难度固定预算为 300/600/1200 秒和 60/120/240 次工具调用。
使用 P1–P3 后选定的同一候选本地配置。任务结束后由独立评分器验收文件/状态，
保留原件不变、修改范围正确、产物保存和内容正确等检查；界面“完成”不等于通过。

输出：每族每级的成功次数/总次数、成功任务耗时、失败耗时、部分进度、人工接管
次数、第一处错误及资源。三次试验只能形成初步边界，不能宣称生产可靠率。
较难级别失败不跳过、不放宽评分。已知基础设施失效单列，修复后的新试次另记。

### P5：在稳定的本地流程上检验 KVMem

选四个固定任务（两个短历史、两个确实超过检索阈值的长历史），KVMem 开/关
各三次，共 24 次。任务、thinking、DFlash2、快照、等待和任务预算一致，配对
次序交错。长历史应来自有用的任务材料和操作，不靠重复无关截图填充。

真实任务报告产品配置整体的成功率、任务耗时和资源；明确列出前缀复用、查询
刷新等配置差异，不冒充“只改变 KV 选择”的实验。必要时另做固定输入重放，
两侧关闭前缀复用，分析推理耗时和历史信息保持；重放结果不算任务成功。

指标包括任务成功率、正确产物率、成功耗时、每步延迟 P50/P95、推理等待、GPU/CPU
内存、上下文及检索 token、历史事实保持、恢复开销、每任务记录体积。
长历史容量失败仍是结果；不能只给一组删截图或降低上下文来制造可比成绩。

### P6：回到原十个复杂场景；然后才评估顾问

完成纯本地诊断报告，明确哪些任务能做、哪里会失败、哪些改进被验证后，回到
原十场景计划，补齐材料/评分的已知缺口，冻结正式 V0，并进行原定配对和 V1 对照。
本轮诊断候选用 D0/D1 等单独版本命名，不直接覆盖正式 V0/V1 身份或历史结果。

Super-Advisor 仅在本地剩余瓶颈已分类后进入下一阶段；本阶段不实现其接入、
不执行顾问调用，也不将顾问协助结果混入本地能力成绩。

## 4. 每阶段执行纪律与报告

- 一次只启动当前阶段的小批次。先完成 P0 和 P1 初始样本，不一次启动全部长任务。
- 每阶段先冻结样本和评分，再执行、定位首次错误、选择改动、固定候选并复测。
- 对阶段缺陷做有界诊断；若一轮修复后仍不能解释，记录未决问题，继续不受影响
  的诊断，不反复扩大平台验收而不测模型。
- 首批保留样本和有意义的重复全部保留；不对已经通过且代码未改变的层重复检查。
- 结果按 `planned / running / passed / failed / timed_out / infra_invalid / blocked`
  记录；计划中的数量不能写成已执行数量。
- 无人干预成功、人工协助成功、部分完成、模型失败和基础设施失效单独呈现。
  卡死更快被发现不等于业务成功率提高。
- 截图和连续录像用于复盘；视频时间轴标记模式、第一次错误、故障/恢复和终态。
  字节相同的截图按内容哈希只存一份，请求记录保存引用和足以复现的清单；若改变
  日志格式，先验证历史重建完整。证据卷、共享目录和 VM 磁盘分别检查空间，设置
  单次证据预算及低空间受控停止，保留既有原始证据。
- 每阶段交付一个报告和可回放的失败样例：本轮测了什么、发现什么、改了什么、
  改善是否经过同条件验证、下一阶段测试什么。

每条记录至少包含：`sample_id`、开发/保留分组、源码与配置身份、输入与答案哈希、
真实请求中的模式、执行顺序、重复编号、开始/结束时间、token/工具预算、原始输出、
独立评分、证据路径，以及首次错误类别。首次错误按感知、事实提取、推理、动作选择、
动作投递/焦点、恢复、结果验证、基础设施、未能归因记录，可附次生错误，不重复计算
同一故障的后果。无关环境失效同时报告其数量与总尝试数，不能只报告有效试次成功率。

耗时拆为取屏/传输、模型首输出等待、模型完整响应、工具执行和界面稳定等待。
阶段报告保留逐试次数据；P50/P95 标明样本量，小样本不据此宣称稳定尾延迟或显著收益。
流程优化的收益只从同条件的原版/候选配对得出，不能拿 P4 候选成绩与旧异条件记录相减。
