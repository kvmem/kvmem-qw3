# BF16 target KV integration

**RETIRED:** the user explicitly removed new BF16 target-weight and BF16-KV
support from scope. The implementation and active tests described here have
been removed. This document preserves historical evidence only; it is not a
current support or reproduction guide. Current target: Q8_0 weights + FP8 KV.

This is an implementation and correctness stage of the active DFlash 2 goal.
No public performance gate has been run or passed.

## Implementation

`--kv-dtype bf16` allocates actual BF16 target and built-in MTP KV tensors,
including the global continuous-batching pools. Five KV append entrypoints
round FP32 inputs to BF16: scalar, contiguous batch, host/device page tables,
and ragged per-request page tables. Local paged prefill recognizes BF16.

FlashInfer single decode, causal verify, paged decode/prefill and ragged
decode/prefill now dispatch on FP16/BF16 explicitly. Decode retains FP32 Q;
tensor-core prefill packs Q to the selected KV dtype. Output and split-K merge
scratch also use that dtype before unpacking to the native FP32 residual path.
BF16 values never pass through FP16 storage. Existing FP8 adapters are unchanged.
The CUDA translation unit includes the adapter headers directly, replacing
duplicated declarations that could drift from their definitions.

BF16 attention requires the FlashInfer build. Unsupported launches return an
error before any FP32 fallback can misread a two-byte cache. KVMem BF16 is
currently rejected by `configure_kvmem`: retrieval, re-RoPE, raw-K storage and
archive paths need explicit BF16 support and validation. KVMem's already tested
FP16 route remains available. This restriction is an unfinished integration
item, not a change to the goal's scope.

Matching target KV storage removes one precision difference from the reference
comparison. It does not imply all-BF16 or bitwise upstream equivalence: QW3 still
uses FP32 main residuals and draft attention/cache, and its reduction order can
differ from SGLang. These differences must remain explicit in benchmark reports.

## Operator and state evidence

- `qw3-flashinfer-bf16-gqa`: eight shapes, three repeated calls each, dimensions
  128/256, GQA 6, causal decode and prefill, permuted pages and guarded row
  strides, against an independent double-precision softmax oracle. Maximum
  observed absolute error 0.000402018 (declared bound 1/256 at |V| <= 0.5).
- `qw3-bf16-kv`: all five append paths match CPU round-to-nearest BF16 bytes
  exactly, including untouched slots, odd widths, ragged positions and padded
  input rows. Twenty-eight attention cases cover three independent request
  lengths up to 16,387, contiguous/paged/ragged routes, verify sizes 7/11,
  gating, guarded output strides and V magnitudes of 0.25/100,000. The large
  values exceed FP16 range and detect incorrect temporary-storage dtype.
  Maximum observed relative mean-oracle error 0.00344267 (bound 1/128).
- The six selected FlashInfer CTests, including the existing FP16/FP8 decode,
  prefill, asynchronous metadata lifetime and plan-cache regressions, pass.
- Compute Sanitizer memcheck for `qw3-bf16-kv`: zero errors.
- All 32 host CTests pass.
- The real production probe passes 44 dense BF16-KV checks across plain and
  DFlash (limits, penalties, thinking budget, EOS, cancellation/retry and both
  sampling policies). FP16 normal/bounded KVMem regressions pass 32 each on the
  same rebuilt binary; `bf16_stage_backend_runs_01.json` records provenance.
- Real BF16-weight/BF16-KV target: rejecting suffixes after accepted lengths
  1..7 leaves captured features and the next three continuation logits exactly
  unchanged. Paired target/draft snapshot restoration is exact; target-only
  restore starts an empty draft at the target position.

Raw logs are retained under `benchmark/dflash2/bf16_*`. Initial compile failures
are retained too; build 05 includes the local paged BF16 route.

## HTTP and continuous-batching qualification

`bf16_http_runs_01.json` records the exact current binary hash, launch arguments,
probe commands, responses and intentional server shutdowns. Five routes pass
17 raw-completion checks each: plain, built-in MTP, DFlash, continuous plain and
continuous MTP. Coverage includes both sampling policies, string/token prompts,
seeded repeats, streaming/usage, cross-chunk stop, Chinese UTF-8 and disconnect
recovery. The continuous configurations also enable prefix caching.

Each continuous route completes eight concurrent 64-token sampled requests.
The plain trace proves kernel batch 4; MTP proves ragged verifier requests 4.
These are actual batched execution checks, not just simultaneous client calls.
They do not establish serial/concurrent output equality, public workload
quality, or throughput. DFlash continuous batching remains unimplemented.

The initial orchestration stopped after the first successful route because its
port-availability probe encountered TIME_WAIT. The retained continuation script
uses a fresh ephemeral port per server and completes the other four routes.
No model/server failure was involved.

## Open serial/batch numerical gate

The three 64-token target probes pass greedy equality for mathematics and code.
The Chinese prompt diverges at zero-based output index 41:

| Logit | Serial | Verifier |
| --- | ---: | ---: |
| token 198 | 27.9694 | 27.9836 |
| token 95826 | 27.9570 | 27.9930 |

Replaying the same 15 target blocks and accepted lengths with no draft calls
reproduces the verifier logits exactly. Disabling
`QW3_BF16_SMALL_PAIR_MAX_ROWS` and enabling local paged BF16 do not remove the
divergence. Both failed gates and their binary hashes/arguments are recorded.
This demonstrates a target serial/batched arithmetic difference, while the
rollback checks exclude rejected suffix state leakage in the tested cases.
It does **not** close the output-correctness gate or establish unchanged quality.

## Short diagnostic timing, not public performance

**Later audit correction:** weight precision must be explicit. These runs use
BF16 target weights; they do not replace the deployment's Q8_0 baseline. The
legacy plain KVMem timer below includes post-prefill selection/replay whereas
the DFlash timer excludes it. Preserve the raw observations, but do not divide
their decode rates to claim a speedup. The current plain route reports these
phases separately (`timing_version=2`). See
`docs/dflash2_fp8_kvmem_20260924.md` for the corrected timing audit.

The production probe on RTX PRO 6000 Blackwell (BF16 weights and target KV)
measured 25.02 versus 139.03 decode tok/s for plain versus DFlash on one
23-token prompt / 64-token greedy completion. With temperature 1, top-k 20,
top-p .95 and top-k-first filtering, the same prompt / 32-token completion
measured 24.10 versus 74.23 decode tok/s. These are single diagnostic cases;
no repeated public speedup is established. Decode excludes prefill. Exact
framework timings, outer wall times and source log hash are retained in
`bf16_short_diagnostic.json`. The sampled DFlash case spends approximately
0.100 s of its 0.431 s decode interval in CPU sampling, a concrete next
optimization target.

The FP16 KVMem sparse-query diagnostic (848-token request after history prefill,
256-token working set, 32 greedy output tokens) measured 20.65 versus 84.71
decode tok/s, plain versus DFlash. Outer request wall times were 2.82221 versus
1.86094 seconds: 11.34 versus 17.20 output tok/s including request work. This
illustrates why decode speed alone must not be substituted for end-to-end
KVMem performance. It is also a single functional probe, not the public matrix.

## Reproduce

Use the existing CUDA 13 / SM120 FlashInfer build configuration described in
`dflash2_implementation_status_20260924.md`.

```bash
cmake --build build-dflash-flashinfer --target qw3 qw3-bf16-kv qw3-flashinfer-decode-gqa qw3-flashinfer-plan-cache qw3-dflash-target-probe -j 4
ctest --test-dir build-dflash-flashinfer -R 'qw3-bf16-kv|qw3-flashinfer-(decode-gqa|prefill-gqa|prefill-queued|bf16-gqa|plan-cache)$' --output-on-failure
/usr/local/cuda-13/bin/compute-sanitizer --tool memcheck --error-exitcode 99 build-dflash-flashinfer/qw3-bf16-kv
# Expected to fail the unresolved Chinese serial-greedy gate:
QW3_KV_DTYPE=bf16 build-dflash-flashinfer/qw3-dflash-target-probe models/Qwen3.8-27B-BF16 models/Qwen3.8-27B-DFlash2-BF16 64
```
