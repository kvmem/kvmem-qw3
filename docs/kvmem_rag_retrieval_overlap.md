# KVMem / AgentLongBench RAG retrieval-overlap analysis

The paper-oriented record of the final numerical results, evidence-gap
analysis, and selected-text dense-replay control is maintained in
[`kvmem_rag_agentlongbench_results.md`](kvmem_rag_agentlongbench_results.md).

This diagnostic compares KVMem's post-prefill selected blocks with the frozen
52-sample RAG delivery at:

`/home/chaidi/kvmem_eval/rag_blocks_52_delivery`

It is diagnostic-only. The new request metadata and dump fields do not
participate in KVMem scoring, selection, attention, or generation.

## Identity and block-definition invariants

The analysis refuses to run unless all of the following hold:

1. `overlap_{0,4,8}_blocks.jsonl` each contains exactly 52 unique
   `stable_sample_id` values in identical order.
2. The KVMem dump contains those exact IDs in that exact order, once each.
3. Every delivered RAG block can be regenerated byte-for-byte using the local
   Qwen tokenizer.

The delivery's block definition is:

- history: non-system messages transformed by canonical `message_to_text()` and
  joined with `\n\n`;
- block size: 32 Qwen tokens;
- step: `32 - overlap`;
- block `i`: `[i * step, min(i * step + 32, history_tokens))`;
- ID: `mflat_c{i:05d}`.

KVMem's internal block ID is different: it is aligned to the fully rendered
chat prompt, including chat framing, instructions, history, and question. It
must never be compared directly with `mflat_c...`.

The analyzer maps KVMem-selected prompt tokens back to separator-free logical
message-text coordinates, then projects that coverage onto the exact RAG grid.
Only after this projection are same-ID set metrics computed. This also handles
an important source-format difference: the canonical KVMem FullContext prompt
joins messages with one newline, while the delivered RAG chunks use two.

## Capture

Run the end-to-end capture and analysis with:

```bash
scripts/kvmem_eval/run_agentlongbench_rag52_overlap.sh
```

The capture sends the canonical prompt with `max_tokens=1`. KVMem finalizes the
post-prefill retrieval selection before generating that token, so no second
full answer-generation pass is needed. The retrieval-relevant configuration is
the original 32K setup: block size 32, mean-k, sink 8, recent 0, no sub-block,
query-conditioned selection, and a 32K generation reserve.

The server is launched with `QW3_KVMEM_DUMP_SCORES`. The request carries:

- `kvmem_trace_tag`: the exact `stable_sample_id`;
- `kvmem_context_span`: UTF-8 byte bounds of the canonical flattened history;
- the existing `kvmem_query_span`.

Dump schema `qw3_kvmem_retrieval_dump.v2` adds the trace tag, rendered-prompt
context bounds, prompt token count, and exact token IDs for selected blocks.
The analyzer independently renders the chat prompt and requires every exported
selected token ID to match before it reports overlap.

## Outputs

The output root contains:

- `kvmem_retrieval_dump.jsonl`: raw meta, all internal block IDs/scores, selected
  flags, and selected token IDs;
- `capture_manifest.jsonl`: prompt hash, exact sample ID, byte spans, and timing;
- `analysis/per_sample_overlap.jsonl`: per-sample selected KVMem text/spans,
  exact RAG IDs, projected same-ID sets, and overlap metrics;
- `analysis/overlap_summary.json` and `.md`: overall, outcome, task, and length
  group summaries.

The primary metrics are logical-text coverage Jaccard, RAG coverage by KVMem,
and KVMem coverage by RAG. Same-ID Jaccard is reported at any, 50%, and full
coverage thresholds after projection to the exact RAG block grid.

## Interpretation

Low source-text overlap directly shows that the two retrievers selected
substantially different evidence. High overlap does not, on its own, prove that
contextualized KV is better than retrieved text. Prompt formatting, block order,
neighbor coverage, and generation variance remain confounders. A stronger
representation test must replay identical source spans through both systems (or
force KVMem to use the RAG-selected spans) while holding the remaining inputs
constant.
