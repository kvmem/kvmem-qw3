## 基线和优化怎么比较

两个流程版本固定命名：V0 为共用平台准备后保留原 agent 策略的版本；V1 为
根据证据选出的优化版本。共用工具能力、模型、DFlash、任务、素材、评分器、
快照、预算和录屏参数相同，仅 agent 流程包不同。

| | KVMem off | KVMem on |
| --- | --- | --- |
| 原流程 V0 | 原始产品基线 | 原流程中的 KVMem 效果 |
| 优化流程 V1 | 不依赖 KVMem 的流程收益 | 流程与 KVMem 配合后的效果 |

主要比较有两条：同一行看 KVMem 开关差异，同一列看流程改动差异。不能只比较
“V0+off”与“V1+on”，那样无法分清两种变化的作用。

当前 on 含前缀复用，off 没有等价的 dense prefix 实现，因此主表是完整产品
配置比较。需要解释引擎原因时，从两侧轨迹共同冻结相同输入，单独进行禁用复用
的 on/off 控制和 on 内部 reuse 消融；这些请求不得混入桌面任务成功率。

### 数量与预算

- 首先完成 V0 的 20 次；若平台、任务、模型及评分口径未变，它们计入后续矩阵。
- V1 首轮再做 20 次，共 40 次，获得全部 10 场景的流程前后比较。
- 稳定性阶段每场景每组合总计 3 次，即 **10 × 2 流程 × 2 策略 × 3 = 120 次**。
  这是原单流程 60 次计划的扩展，包含前述 40 次；开发诊断单独标识、不混入正式统计。
- 若优化结果无收益，保留 V0，输出失败/回退分析；不强行推进昂贵的重复 V1 试验。
- 沿用预跑后固定的 30/60/90 分钟预算。按当前初始预算，20 次执行上限 22 小时，
  40 次 44 小时，120 次 132 小时，另有准备和复位开销。这是最坏预算，不是完工承诺。

首轮每对顺序均衡为 on→off / off→on；后续已冻结的四组合按预定种子平衡
顺序，在同一 GPU 串行运行。记录运行时段和资源干扰，承认首轮 V0 早于 V1。
排队顺序种子和模型采样种子分别记录；配置未支持/未设置模型 seed 时写 null，
不能把调度种子冒充模型随机数控制。

## 如何从实际运行定位改善空间

对每次失败或异常慢的运行生成一张诊断记录：场景/版本、最后完成里程碑、
**第一个偏离目标的动作或状态**、后续无效工作、直接证据、怀疑原因和置信程度。
优先解释首次错误，避免把最后一个超时误判为根因。多原因分别标注主因、次因；
证据不够时写“未确定”，用最小诊断补证据。

| 类别 | 要看的证据 | 候选改进及验证方式 |
| --- | --- | --- |
| 环境/工具缺口 | 应用未启动、字体不一致、网站不复位、工具不支持 | 修共用平台或任务；相关配对作废并保留记录，重新冻结；不计作策略收益 |
| 定位/焦点错误 | 点击坐标、控件提示、前台窗口、错误输入落点 | 使用已有可见控件提示，输入前验证焦点；看错误输入/返工是否减少 |
| 工作流遗漏 | 页面看过但项目未做、最后缺行/附件、任务提前结束 | 显式里程碑与待办状态、逐项对账；核对遗漏率和严格成功率 |
| 历史/修订误用 | 信息出现时刻、消息更新、引用来源、错误发生时长度 | 带来源和版本的工作笔记；更新时使旧结论失效；核对 035/043/080 的字段 |
| 观察/调用冗余 | act 已回截图后立即 observe、相同画面/动作循环 | 复用有效动作回执的观测；在界面确实变化或加载时才再观察；统计省下的调用与延迟 |
| 恢复策略不足 | 弹窗、保存失败、失去焦点、不确定动作回执 | 按可识别状态选择有限恢复；不确定投递先对账，不能盲目重发或自动越过暂停 |
| 完成核验不足 | 声称完成但文件未保存、导出错路径、提交未生效 | 在关键里程碑确认实际状态，交付前核验保存/导出；检查假完成下降及额外成本 |
| 推理/资源瓶颈 | 阶段计时、prefill、前缀命中、GPU/RSS、上下文长度 | 引擎问题单独控制实验，保持 agent 比较的引擎不变；避免把降采样或截历史收益算成 KVMem |

优先级按“受影响场景数、导致失败次数、可避免等待总量”排序，先处理影响
严格完成率的问题，再处理相同质量下的等待。每轮最多选两个独立候选，先逐项
验证再组合；多个改动一起上而无法归因时，不宣称已确定原因。

## 计划评估的 agent 流程

下面是候选设计，**不是已经证明有效、也不是全部预先加入基线**：

1. **任务开始**：提炼交付物、约束和 3–6 个可检查里程碑；只使用用户任务和
   已看到的信息，不读隐藏答案或评分器。
2. **执行中**：维护轻量工作笔记，记录“已做、待做、依据、修订、当前应用”；
   跨应用和长任务恢复时核对。笔记本身也进入两侧 token、耗时和工具预算。
3. **每个动作后**：先利用 act 回执中的有效截图；遇到加载/弹窗/失焦才重新
   观察或走恢复路径。当前 60 秒观测有效性、动作去重和暂停机制继续生效。
4. **每个里程碑后**：核对当前进展和剩余条目；新增规则到来时重新检查受影响
   结果，避免整段流程无差别重做。
5. **结束前**：核对实际成果、保存位置、必要提交状态；未完成则明确报告，
   不以生成了最后一段自然语言作为业务完成。

若工作笔记需要新增工具，只能读写 agent 自己看到的状态，原有桌面信息能力
保持不变；新工具只属于 V1 流程包，两种 KVMem 策略都能用，并计入调用成本。
不向代理开放网页隐藏状态 API、宿主机 shell、评估答案或直接文件生成捷径。
原任务明确禁止的操作仍然禁止。工具能力变更与提示词变更分别做消融。

### 避免对这 10 道题做答案式调优

013、004、006、010、022、035、038 用于诊断开发。043、080、051 的运行证据
保存，但在 V1 冻结前不用于逐轨迹调优；将它们作为检查策略迁移的三项场景。
这不是完全未知的任务集，也不能证明泛化能力，只能减少针对某条失败路径写脚本。
人工设置/判分器正确性检查仍须覆盖全部 10 项。

任何发现通用平台/评分错误的保留场景都先修复并重建基线，不靠隐藏错误维持
所谓独立性。给某任务补明确业务信息、改答案或增加特定参考坐标，均属于任务
版本变化；不能宣称是通用 agent 优化。

## 接受优化的规则

先看同一 KVMem 配置下 V1 相对 V0 的逐场景结果，再看整体。预期收益方向：
严格成功率提高、遗漏/错误/返工下降，或在效果不下降时等待减少。这里不承诺
具体提升百分比，也不会按看到的结果临时更换主要指标。

- 新的重复提交、错误覆盖、越过暂停或不确定动作盲目重发，直接阻止该候选采用。
- 出现 V0 成功、V1 失败的场景必须逐项解释并复现；不能用别的容易任务变快抵消。
- 仅在两侧均成功的同任务配对报告完成时间比；超时保留为未完成，不能伪装速度提升。
- 10 场景等权，按场景给出严格成功和分项，不只给全体动作的均值；P95 注明样本量。
- 统计分组单位是场景，三次重复不当作三个独立业务场景；小样本先报告原始分布。
- 没有可重复收益就保留 V0 和候选失败证据。明确模型视觉/知识限制、工具限制和
  推理资源限制，避免继续叠加提示词造成更多等待。

## 交付及进度记录

每次运行先登记 run ID、场景、流程版本、KVMem、重复编号、全部身份和预算，
结果写入新目录。状态区分 planned/running/passed/task_failed/timed_out/
resource_exhausted/infra_invalid/grading_failed/interrupted，不能将缺失结果默认成功。
评分器失败记分数未知，不记模型通过；修好评分器可离线重评同一产物并记录版本。

每轮结束输出：

- 10 场景完成矩阵及缺项，全部有效运行分母、无效/重跑次数。
- 每场景的首次错误、业务分项、等待分解和资源曲线。
- KVMem 开/关、V0/V1 两种方向的同时间轴双栏视频；保留完整原片和失败结尾。
- 输入、输出、视频、事件及判分证据清单，避免真实凭据进入录像或公开材料。
- 优化补丁及单项验证、回退记录、保留候选理由和未解决问题。

阶段转换、基础设施阻塞、完整一轮结束或出现明确回退时更新进度；无需每个
动作都汇报。现场推理仍由当前 Linux GPU 宿主机承担，Windows VM 运行 agent
客户端和被操作的应用；这些数据不能直接当作普通 Windows 物理机的推理性能。
