# Windows computer-use 能力边界测试

当前优先级按用户要求调整：先用由短到长的自定义任务确认能完成的操作，再继续原 10 个复杂 OSWorld 场景。原实验和失败不删除；自定义任务不算官方 OSWorld 分数或原任务正式基线。

## 最近复杂任务为何零通过

- 预检大多只有 60–180 秒，严格判分要求完整、保存后的交付。038 已改对一条线索，但没有完成全部线索；043 主要在阅读。它们说明部分进展，不是完整成功。
- 有真实推理与操作问题：013 在 900 秒内仍违反预算、奖项比例和金额差约束；035 重复点错联系人；080 窗口焦点错误后反复新建空白工作簿。延长时间不能保证解决。
- 平台问题已独立处理：PDF/图片关联此前造成工具拒绝；051 修复后 26 次动作全部完成、零拒绝，但仍未完成图层编辑和保存。站点装饰图片、字体已改为离线。
- 历史基础测试曾通过：windows-native-type-pilot-01 的记事本 off；windows-native-resource-pair-01 的记事本 on/off；windows-native-pilot-01 的网页填表 on。旧客户版本、快照和预算不同，不能与新结果混合计算收益。

## 新任务及方法

cap01 创建保存记事本；cap02 修改已有笔记并保留原文；cap03 从浏览器提取代码并保存；cap04 填表下载 JSON；cap05 表格行公式及求和；cap06 文档标题及两处文本替换；cap07 指定幻灯片编辑及删除；cap08 跨应用读取新旧规则并计算；cap09 文件改名移动并保留无关文件；cap10 表格整行排序及求和。

先跑 cap01–04 的 on/off 配对，前两项 300 秒、后两项 600 秒；再按执行轨迹增加办公与规则任务。每次恢复相同快照、使用相同提示/预算和视觉历史策略、实际 QW3+DFlash2、原生 Codex 客户端及只读连续录屏。默认 legacy 应用入口已有本地网页，不修改执行器、已验证客户端或快照。

独立验收最终导出的实际字节，保留完整成功、部分检查比例、首个错误、任务耗时、推理等待、动作数和拒绝数。模型宣称成功不等于通过。每任务单次配对只用于摸底；稳定性需重复验证；短历史结果不能证明 KVMem 的长历史优势。

## 结果

第一批 4 个自定义场景、8 次实际模型运行完成：7 次通过独立验收，8 次基础设施与录屏链路均有效。

| 场景 | KVMem 开 | KVMem 关 |
|---|---|---|
| 创建保存记事本 | 通过，36.8 秒 | 通过，57.7 秒 |
| 修改两处笔记、保留原文件 | 通过，80.3 秒 | 300.3 秒超时，未保存 |
| 浏览器代码→记事本 | 通过，43.3 秒 | 通过，101.1 秒 |
| 网页填表下载 JSON | 通过，42.3 秒 | 通过，81.8 秒 |

cap02 关闭版本最终截图独立查看确认标题、Owner、Approved 和 Hours: 8 都正确，但仍停在查找替换界面，没有目标文件。22 次推理累计约 276.7 秒、20 次桌面动作全部完成。它属于预算和步骤数导致的交付失败，不是已证明不会编辑。后续增加预算复测；失败记录保留。

两次 cap01 都出现打开应用后焦点仍在桌面、首次输入无效，随后点击编辑区并重试成功。cap03 开启版还有动作 ID 长度错误后重试。动作接受率、工具参数错误和任务成功率分开记录。

已观测可完成：基础文件创建保存、受约束文本修改、跨应用提取和简单网页提交。稳定可靠性仍待重复验证。第二批将测试公式、文档、幻灯片、新旧规则、文件整理与整行排序。

这些是每配置单次摸底，不能形成显著性结论。开启版本启用当前产品的 KVMem 前缀复用；关闭版本没有该能力，差异不能全部归因检索机制。第一批最长输入约 79K token，尚不足以检验很长历史的记忆保留。任务计时不含快照恢复和模型加载，录像包含启动与收尾。

第二批首条 cap05-on-01 的保存文件通过全部公式与计算值检查，但原生客户端收尾的 legacy /files 对被 LibreOffice 占用的 outputs/cap05.xlsx 使用 ReadAllBytes，导致 infrastructure_error。独立二进制收集成功，连续录像完整；这条是无效测试，不计入完整通过或模型失败。队列正确停止并保留其余 11 条未运行。
