# Windows computer-use 当前能力边界

原来复杂任务的零完整通过不能概括为“不会操作电脑”。已完成新选的 10 个自定义能力场景首次开关配对：20 条有效试次，18 条按时完整通过、19 条产物正确。KVMem 开 10/10，关 8/10。另保留 3 条环境／收尾链路受阻试次，均未删除或算作有效模型通过。追加笔记 600 秒同条件配对也已完成，两侧均通过。全部 25 条尝试中 22 条有效、20 条按时完整通过、21 条产物正确。

这些是实际 Windows VM 中的本地 QW3 + DFlash2、原生 Codex 和 Computer MCP 运行，全部保留连续录像及独立文件验收。自定义场景不是官方 OSWorld 分数；原 10 个复杂场景正式运行仍为 0，V0 未冻结，V1 未实施。

## 原来为什么全零

1. **预算不足及未完整交付。** 多数复杂预检只有 60–180 秒。038 改对了 1 条线索，但未完成全题；043 主要在阅读；004、010 在 60 秒停止。严格完整判分会记为 0，部分进展另外保留。
2. **确有推理与定位失败。** 013 在 900 秒内仍违反奖品预算与比例约束；035 想点 Emily，却三次点到 Mike；080 丢失焦点后反复打开空白工作簿。单纯增加时间不能保证解决。
3. **共同环境故障。** PDF、图片和办公／文本文件自然打开时的默认应用弹窗会被执行范围拒绝。051 修复图片关联后 26 次动作全部完成、零拒绝，仍未完成和保存，说明环境故障不是全部原因。
4. **本次发现了验收器误判风险。** LibreOffice 改变 PPTX 正文占位符编号，首次评分器读取固定 idx 时异常。原复杂任务不能未经证据一概归因于评分器，但本次校准中这两条误判已修正并保留原始判分。
5. **043 的严格业务检查还有口径限制。** 原材料的参会人与评分规格存在差异；额外工作时间检查把“正常工作时间”解释为各地区 09:00–18:00，这个明确标注的诊断解释没有洛杉矶、伦敦、新加坡三地共同区间。官方兼容分、结构检查和该诊断必须分别报告，不能将诊断的零结果直接视为模型失败。此前 180 秒预跑的原评分本身也为零，因此该限制并不能解释那次预跑的全部失败。

## 可以确认的范围与未确认的上界

- 已观察可完成：短文本交付、简单网页操作、基础文档和演示文稿修改、几行表格的公式／排序、两版明确替代规则、少量文件改名与移动。
- 测试规模为 4 条数据行、3 张幻灯片、2 版短规则、3 份文件，不能推断大批量和长流程可靠。规则任务的两版实际截图已查看，新版替代声明和计算数据可见。文件整理两侧三份实际字节均与固定原件一致，包括编码和换行。
- 未验证稳定可用：原场景的多材料消歧、复杂约束规划、20 场会议与 40 条线索、精细 GIMP 图层编辑。已有预检失败保留，尚不能从预算受限的结果精确确定这些能力的绝对上限。
- 单次配对是可行性摸底，不是可靠性、显著性或长历史记忆结论。实际能力任务的最长有效输入约 173,888 token；另行完成的近 1M 合成压力输入仅验证两枚标记在压缩后保留，不代表复杂业务语义保持。

## 延迟与可改善之处

排序两侧分别 33／32 次动作，全部执行；开启版 127.8 秒、关闭版 685.5 秒。推理等待合计约 90.6／634.4 秒；首 token 中位数约 0.79／12.17 秒。关闭版已计时服务器请求的约 90.6% 耗时在首 token 前。该组比两侧路线差异较大的任务更利于观察延迟，但仍不是严格重放同一轨迹的引擎对照。

当前产品配置的开关包含前缀缓存差异；不能把全部时间差归因于 KVMem 检索本身。采样的整卡峰值约开 45.6 GiB、关 67.7 GiB，包含相关进程，不是隔离的模型峰值。任务计时不包含快照恢复和加载，录像包含启动与收尾。

最多两个后续通用流程候选尚未实施：

1. **稳定交互与参数合同。** 明确文件／窗口身份与焦点，避免反复启动空窗口；处理动作 ID 格式造成的额外调用。本批已观察 31 次 ID 格式错误，动作接受率不能代表全部调用合法或操作正确。
2. **减少重复处理和无效复查。** 基于实际风险选择复查步骤，研究历史输入与前缀复用开销，保留关键规则和独立验收；不能通过丢失必要历史或削弱验收制造改善。

两次创建笔记都曾打开应用后焦点仍在桌面，首次输入无效，重新定位后成功。两侧表格 Save As 都曾遇到完整路径输入后 Save 不可点击，导航 Desktop 后成功。上述轨迹是候选依据，尚未宣称 V1 或提示修改有收益。

另行进行的[长历史压力诊断](computer_use_windows_long_context_boundary_20261002.md)发现并修复了缓存恢复边界错误：旧检查点之后的已完成历史被当作当前必需后续内容，导致选择超预算。原始六条输入修复后均可执行，未增加选择预算。此故障发生在明确标注的合成大观察压力输入，不能反过来解释此前所有复杂任务的零分。

修复后原生开启版首次复测完成约 883K 输入；关闭版也能独立完成同一输入，但冷处理用时约 929 秒。945K 的原生压缩请求首次因 180 秒读超时失败，磁盘写满又损坏收尾录像；失败和恢复片段均单独记录。随后使用客户端 14、连接心跳及明确延长的诊断等待，实际 945,446 token 压缩请求在约 493 秒完成，17 次观察和首尾标记全部正确，独立审计通过，连续录像完整。任务和选择预算未提高，生产默认等待未改；关闭版同规格原生压缩尚未验收。业务能力任务的 25 段完整录像不受影响。这些共同平台修复不是 agent V1 或新增业务任务通过。

## 环境与评分修复证据

- cap05-on-01 的产物正确，但 legacy `/files` 把被 Office 占用的二进制当文本读取，收尾失败；记录保留。新办公场景改用原 OSWorld 办公适配同样的 Desktop 交付与显式二进制收集。通用产品二进制列表缺陷仍需修复，未宣称路由调整消除了该缺陷。
- cap05-on-02 的 XLSX 打开出现 OpenWith。中性办公默认确认后，首个快照因偏好清理丢失 xs 命名空间而验证失败，旧候选保留；现用 lxml 保留 QName，仅清理中性 MRU。办公 v2 已完成实际恢复与三次执行器验收。
- cap08-on-03 的 TXT 打开也出现 OpenWith。管理员依据录像暂停该条；第一次暂停脚本使用了错误的任务字段，没有回执，脚本仍保留；第二次核对正确字段后暂停成功。恢复干净办公 v2 后，用中性文件确认 TXT 默认 Notepad，归档清理资格文件、标签和最近记录。新快照 `qw3-osworld-office-text-20261002` 实际恢复后八类关联保留，文本与三类办公文件自然打开，四次真实执行器操作接受，最终恢复干净。
- cap07 两侧按真实标题与全部非空正文复核；不依赖内部占位符编号。缺正文、额外文字及未修改原稿不能通过。复核先验证二进制收集回执、原结果和文件哈希，只写 `independent-grade-v2.json`，原模型结果与错误评分不改。后续评分器和冻结来源已接入修正。

10 个能力场景使用的客户端 13 和执行器未改变；后续长历史诊断使用的候选客户端 14 单独说明。这些共同平台与评分修正不计为 agent 改善。
